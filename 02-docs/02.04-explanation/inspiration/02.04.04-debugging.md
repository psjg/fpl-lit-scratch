# 02.04.04 2026-10-21 — Debugging, and the playground as an accessible IDE

What would top-tier debugging look like for FPL, and how does the playground grow into an
accessible IDE that has it? This note maps the lineage onto FPL's own shape, names what the
first prototype does, and lists what waits. Claims are tagged **[src]** (read in a primary
source, URL in [Sources](#sources)), **[meas]** (measured here) or **[prior]** (our
inference, untested).

## What FPL already has

- The evaluator is a pure step machine: `step : State(stack, code, words) -> State`, and
  `final` loops it, one fuel unit per step (`01-bootstrap/python/fpl/evaluate`). Time travel is
  therefore indexing, not recording of the world **[meas]**: re-running the recorded steps is
  deterministic.
- Fuel makes every run finite, so a full trace is bounded by the budget.
- Every front-end pass maps a whole term to a whole term (lex, parse, resolve, expand,
  desugar, elaborate, lower, normalize, optimize), so a pass boundary is a free snapshot.
- Refusals are values with spans (`FplError`), and the REPL already treats out-of-fuel as an
  event, not a crash.

## The lineage, and what transfers

| System | Core mechanism **[src]** | What FPL takes |
| --- | --- | --- |
| rr, Pernosco | Record only nondeterministic inputs; replay is exact; Pernosco builds a queryable database of all states. | The step index *is* the execution point, so no counters are needed. Record the initial state plus effect results; snapshot every K steps; "when did this stack slot last change" is a query over the trace **[prior]**. |
| Elm debugger | Records every `Msg`; pure `init`/`update` make the history replayable; a slider re-renders point N. | The closest match: a trace of states and a slider. Edit-and-replay means re-running against new word definitions; the divergence point is the first differing state. |
| Smalltalk / Pharo | Step into / over / through; restart a frame; edit the method live and continue. Nothing recorded; frames are objects. | Step-over is "run until the stack depth returns"; step-through skips plumbing pushes; live edit swaps a word in `words` and resumes, since `words` is part of `State`. |
| Racket stepper | A step is one reduction shown as before and after with the redex marked. | The stepper's unit and its two-pane (redex, replacement) display. |
| Racket macro stepper | Expansion is a rewrite sequence with hygiene colours and a hiding policy for which macros count as steps. | One trace record for every stage: (stage, rule, before, after, span, provenance). A hiding policy per stage or rule; provenance colouring (source, introduced by pass X). |
| Lisp conditions and restarts | Signalling does not unwind; named restarts are offered at the failing site; the debugger is the default handler. | Refusals, effect denials and out-of-fuel carry restarts as data: grant N more fuel, use a value, fill the hole, deny the effect. The REPL's fuel event is the first instance. Fits the "restarts / supervision" promise in [judgments](02.04.03-judgments.md). |
| Glamorous Toolkit | The moldable debugger: domain predicates over execution state drive stepping and views. | One generic `run-until(predicate)`; stage steppers ("next macro use", "next effect", "next hole") are predicates. Views chosen by activation predicates. |
| Debug Adapter Protocol | `next`, `stepIn`, `stepBack`, `reverseContinue` gated by capability flags; lazy `scopes`/`variables`; stop reasons. | Speak DAP so that other editors can drive the same session: capability `supportsStepBack` is cheap here; custom stop reasons `fuel`, `refusal`, `effect`, `hole`. Granularity is a parameter (a stage name or step kind). |

## The target, in four layers

1. **One trace format.** A frame is `(stage, rule, before, after, span, provenance)`. The
   evaluator frames of the prototype are the `stage = evaluate` case. Fuel counts the same
   frames, so "step 4812 of 10000" is both a position and a budget.
2. **Reverse and branch.** Record states (persistent, shared) with a snapshot every K steps;
   reverse-step is "nearest snapshot, then replay". Edit a word, replay from the divergence
   point, and diff the two traces.
3. **Conditions as the default debugger entry.** A refusal stops *at* the failing frame with
   its restarts listed; the REPL and the playground are two front ends of one handler.
4. **Stage views.** Per-stage steppers and a stage-diff view (term before and after a pass),
   a macro-expansion stepper with provenance colours, and a fuel timeline. Each is a
   predicate plus a renderer over layer 1, in the moldable-debugger sense.

## Accessibility is a design input, not a finish

Rules from the sources, with the inferences marked:

- Everything is operable from the keyboard (WCAG 2.1.1); controls are native elements, one
  tab stop each **[src]**.
- Announcements go to a `role=status` live region, never by moving focus (WCAG 4.1.3), and an
  over-eager live region is itself a failure ("chatty") **[src]**.
- Announcement detail is a user setting, as VS Code separates sounds from announcements
  **[src]**; terse, normal and full are the levels the prototype offers.
- Autoplay announces only "playing" and "paused at step N of M" **[prior]**: no source
  covers screen-reader time travel. Nothing was found on it, which is an open gap in the field.
- The text path comes first: a linear ordered list of every step is the baseline, a graphical
  view an addition **[prior]**. Blind developers fall back to print statements when a
  debugger is not readable (CodeTalk, CHI 2018, a search summary **[src, secondhand]**).
- Shortcuts avoid screen-reader and OS chords (APG list) **[src]**; the prototype binds only
  Escape (pause) and Alt+Arrows (step) inside the stepper **[prior]**, untested with a real
  screen reader.

## The prototype

A **Step** button on `/try` records the buffer's run once (`assets/fpl_steprec.py`, run under
Pyodide) and opens a stepper over it (`assets/fpl-stepper.js`):

- One frame per `step`, the same loop and fuel rule as `final`; a loop is cut at 2000 frames,
  not failed. Recording 100000 frames of a growing-stack loop took 7.5 s natively **[meas]**:
  the printer is not free, so the cap stays small until the trace stores diffs.
- Back, Forward, Start, End, Play, a range input as the position, and a list of every step.
- The editor highlights the source line of the current frame, so a step inside a word's body
  moves the highlight into the body.
- Detail setting (terse, normal, full); `aria-valuetext` on the slider names the step; a
  refusal is announced at the last frame.
- Checks: `assets/fpl-stepper.test.mjs` (the model, `node --test`) and
  `01-bootstrap/tests/test_trace_asset.py` (the recorder, in the gate). Not yet run in a real
  browser or with a screen reader.
