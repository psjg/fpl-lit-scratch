# 02.03.02 2026-09-27 — Surface grammar

The first grammar for the surface syntax, written to be run rather than read: Lark EBNF
with an off-side postlexer, tested against the language drafts, the examples, the paths
example, the planted-tree clauses and a set of enclosure cases (Lark 1.3.1). It sits on
rung **trede 2** of the verification ladder: tests on the same definitions, where the
grammar file is the definition and the harness parses the drafts.

The repository is the canonical copy: [`grammar.lark`](../../01-bootstrap/fpl/grammar.lark),
read by the passes [lex](../../01-bootstrap/01.02-pass/01.02.01-lex.md) and
[parse](../../01-bootstrap/01.02-pass/01.02.02-parse.md); the representations are
[source](../../01-bootstrap/01.03-repr/01.03.01-source.md),
[tokens](../../01-bootstrap/01.03-repr/01.03.02-tokens.md) and
[syntax](../../01-bootstrap/01.03-repr/01.03.03-syntax.md). The grammar is the common
base of three companions: [FON](02.03.03-fon.md) (the data profile), [FML](02.03.04-fml.md)
(the markup profile) and the hand-off record [SHAR](02.03.05-shar.md). Why the syntax is
shaped this way is argued in [syntax rationale](../02.04-explanation/02.04.05-syntax-rationale.md);
the semantics the shapes carry (frames, saturation, effects) are in the
[substrate](../02.04-explanation/02.04.04-substrate.md).

## 1. Layers, and what lives where

| layer | in the grammar? | class | how |
| --- | --- | --- | --- |
| lexing | yes | Type-3 | split on whitespace; only enclosure delimiters and the bar self-delimit |
| token shape (affixes) | no: a regular post-pass | Type-3 per token | prefix sigils `→ $ ../ ..`, infix `/` paths, suffix modifiers; numbers, `∞`, `π` recognised here |
| strings `“ ”` `「 」`, block comments `⟦ ⟧` | no: a counting **pre-lexer** | Dyck, counted per pair | each pair counted by its own opener/closer only; the interior goes to the pair's interpreter; islands `⟨ ⟩` inside `“ ”` are read recursively with the same grammar |
| enclosures `[ ]` `( )` `⟨ ⟩` | yes | Type-2 | one pushdown; newlines inside brackets are not block structure |
| off-side blocks | yes, via postlexer | Type-1 lexer → Type-2 tokens | an indent stack emits INDENT/DEDENT |
| frames (the bar) | yes | Type-2 | `frames: frame (BAR frame)*` |
| named closers (heredocs, `end name`) | **not yet** | Type-1 | belongs in the pre-lexer beside the counted pairs |
| saturation, arity, `+fail`, `+io` | no | typing | a linear pass over the parse, dictionary-dependent |

The table is the security design as well as the parsing design: recognise the input fully
with the weakest sufficient class before processing it (see
[FON, parser dramas](02.03.03-fon.md#6-pre-empting-the-parser-dramas)).

## 2. The grammar (`fpl.lark`)

```
// FPL surface grammar — prototype, 2026-09-27 (revised: printer laws; tabs as indentation and as cell separators)
start: _NL* line*

// A line is a flat program; an optional indented block follows it (children first, post-order).
line: frames _NL block?
block: _INDENT line+ _DEDENT

// The bar separates frames; a run of tabs separates cells within a frame (rank literals: space = token,
// tab = cell, newline = row); in code a tab is simply a cell boundary too. No empty cells: write ⟨⟩.
frames: frame (_BAR frame)*
frame: _TABS? (cell (_TABS cell)* _TABS?)?
cell: item+

?item: TOKEN
     | group
     | quotation
     | prefix

// Enclosures: every one a distinct pair; interiors counted, so they nest in themselves. Each holds frames.
// Strings “ ” and 「 」 and block comments ⟦ ⟧ are counted by the pre-lexer; islands ⟨ ⟩ in “ ” are read recursively.
quotation: "[" _NL* frames? "]"                  // thunk / Code, decided by consumer; the bar is allowed inside
prefix:    "(" _NL* frames? ")"                  // reader op: rotate head to end, bar the arguments
group:     _LANGLE _NL* frames? _RANGLE       // evaluated enclosure: ⟨⟩ the empty list, ⟨1 2 3⟩ a list, ⟨expr⟩ an island in text

// A token is any run of non-whitespace, non-self-delimiting characters (Forth rule).
TOKEN.1: /[^\s\[\]()“”「」⟦⟧⟨⟩|⍝]+/
_BAR: "|"
_TABS: /\t+/
_LANGLE: "⟨"
_RANGLE: "⟩"

// Line comments end at the newline, which is already structural.
LCOMMENT: /⍝[^\n]*/
%ignore LCOMMENT

_NL: /(\r?\n\t*)+/                    // indentation is tabs only: one tab per level
%declare _INDENT _DEDENT
%ignore / +/                          // spaces only; tabs are cell boundaries
```

The comment spelling, the caesura-as-word and the block-comment pair have since changed:
see [spellings and comments](02.03.06-spellings-and-comments.md) (S32, S33, S48) and the
[entries and checks](02.03.08-entries-checks-forcing.md) page (S45 item 5). The code above
is the 2026-09-27 state kept as the record.

## 3. The pre-lexer and the shape pass

```python
PAIRS = {'“': '”', '「': '」', '⟦': '⟧'}
KIND  = {'“': 'str', '「': 'raw', '⟦': 'com'}

def prelex(src):
    # Count each string/comment pair by its own opener/closer, replace it by a placeholder
    # token, keep the interior for the pair's interpreter. Overlap is impossible by construction.
    out, stash, i = [], [], 0
    while i < len(src):
        c = src[i]
        if c in PAIRS:
            close, depth, j = PAIRS[c], 1, i + 1
            while j < len(src) and depth:
                depth += (src[j] == c) - (src[j] == close); j += 1
            if depth: raise SyntaxError(f'unclosed {c} at {i}')
            interior = src[i+1:j-1]
            if KIND[c] != 'com':
                stash.append((KIND[c], interior)); out.append(f'¶{KIND[c]}{len(stash)-1}')
            i = j
        else:
            out.append(c); i += 1
    return ''.join(out), stash
```

Token shapes the pass produces:

| token | shape |
| --- | --- |
| `→k` | prefix `→`, name `k` |
| `$cell` | prefix `$`, name `cell` |
| `../io` | prefix `../`, name `io` |
| `math/mean/doc` | path `[math, mean, doc]` |
| `+´` | name `+`, mods `[´]` |
| `rect⁼` | name `rect`, mods `[⁼]` |
| `word?`, `set!`, `a-b`, `1+2` | names |
| `2`, `∞` | numbers |
| `../store/new` | prefix `../`, path `[store, new]` |

The string `“hello ⟨name⟩ and ⟨1 | 2 +⟩ and $cell” print` pre-lexes to `¶str0 print`;
its interior reads as text `hello `, island `[name]`, text `and`, island `[1 2 +]`, text
` and $cell`.

## 5. What writing it decided

1. **Strings cannot live in the context-free grammar under an LALR contextual lexer**:
   after a closing `”` the merged lookahead admits a text-run terminal, which then
   out-lengths the code token. The fix is the design made literal, not a hack: a counting
   pre-lexer handles each pair by its own delimiters and hands the interior to the pair's
   interpreter ("the pair names the interpreter"), and islands are read by recursion. The
   core grammar keeps only `[ ]`, `( )`, `⟨ ⟩`.
2. **`⟨ ⟩` is one enclosure everywhere**, the evaluated group: `⟨⟩` the empty list,
   `⟨1 2 3⟩` a list, `⟨expr⟩` an island in text. No separate island rule.
3. **A bare modifier is a token** (`]¨`, a `¨` head line): shape kind `modifier`, applied
   to the value below, the same meaning as when attached.
4. Newlines inside `[ ]` and `( )` are not block structure (multi-line quotations); a block
   *inside* a quotation is therefore not expressible. Open whether it should be.
5. Line comments are ignored at the lexer; block comments are removed by the pre-lexer.
   Serialisable comments (trivia by identity) are not produced at this stage: the
   pre-lexer would keep them instead of dropping them (later settled by S33/S48 in
   [spellings and comments](02.03.06-spellings-and-comments.md#5-comments-s33-s48)).

**Not yet** (at this date): named closers (heredocs, `end name`); `¶` placeholders are a
harness device, not syntax; the shape pass does not validate paths against the affix table
(`a//b`); no canonical printer, so `parse ∘ print = id` was untested; the shar delivery
(see [SHAR](02.03.05-shar.md)).

## 6. The canonical printer and the two laws

A printer `pprint : tree → text` and the two laws, checked with Hypothesis:

- `parse ∘ print = id` on trees: `parse(pprint(t)) == t`
- `print ∘ parse = canonicalize` on source: `pprint(parse(pprint(parse(s)))) == pprint(parse(s))`

Two generators. (a) `hypothesis.extra.lark.from_lark` over the **flat fragment** of the
grammar (no blocks: declared `_INDENT`/`_DEDENT` have no pattern to generate from; comments
removed since they are not in the tree; generated lines stripped since leading whitespace
there is `%ignore` noise, not indentation). (b) A hand-written **tree strategy** with nested
quotations, prefix groups, angle groups and up to two levels of indented blocks.

| generator | examples | parse∘print = id | print idempotent |
| --- | --- | --- | --- |
| from_lark, flat fragment | 2000 | holds | holds |
| trees with blocks (depth 2, block depth 2) | 2000 | holds | holds |

The canonical form the printer fixes: tokens separated by one space; frames joined by
`\|`; a line stripped of leading and trailing space (so a leading empty frame prints as
`\| …`, never as a space, which the indenter would read as indentation); one tab of
indentation per block; `[ a b ]`, `( a b )`, `⟨ a b ⟩` with inner spaces and `[ ]`, `( )`,
`⟨⟩` when empty; multi-line quotations flattened to one line; cells joined by one tab; an
enclosure whose body prints empty prints as the empty pair (`⟨⇥⟩` canonicalises to `⟨⟩`).

```python
def p_item(i):
    if isinstance(i, Token): return i.value
    if i.data == 'quotation': return '[ ' + p_items(i.children) + ' ]' if i.children else '[ ]'
    if i.data == 'prefix':    return '( ' + p_items(i.children) + ' )' if i.children else '( )'
    if i.data == 'group':
        inner = [c for c in i.children if isinstance(c, Tree)]
        return '⟨ ' + p_frames(inner[0]) + ' ⟩' if inner else '⟨⟩'

def p_frames(fr): return ' | '.join(p_items(f.children) for f in fr.children)

def p_line(line, depth=0):
    out = ['    ' * depth + p_frames(line.children[0]).strip()]
    if len(line.children) > 1:
        out += [p_line(l, depth + 1) for l in line.children[1].children]
    return '\n'.join(out)
```

(The sketch indents with four spaces; the shipped printer emits tabs, see section 7.)

What the properties forced on the grammar: `start` is never inlined (a one-line program
must still be a `start`); `_BAR`, `_LANGLE`, `_RANGLE` are filtered from the tree (tree
equality is over content, not delimiters); `⟨ ⟩` is tracked by the indenter like `[ ]` and
`( )`, so a newline inside an angle group is not block structure. Two generator artefacts,
not language facts: `from_lark` emits ignored terminals and leading whitespace, both
stripped before parsing.

## 7. Indentation is tabs; alignment is elastic tabstops (decided 2026-09-27)

One tab per indentation level; the file contains tabs, never indentation spaces.

1. **The off-side rule becomes counting, not copying.** With spaces the lexer remembers
   and compares the *width* of the enclosing indentation (the Type-1 leak in the layer
   table); with tabs a level is a count. An over-deep indent (`⇥⇥⇥` under `⇥`) is one
   INDENT and canonicalises to `⇥⇥`; the only remaining indentation error is a dedent to
   a level never opened. After the switch all five sources parse, both printer laws hold
   (2000 examples each), and `a / ⇥⇥b / ⇥c` is rejected as before.
2. **Elastic tabstops (Nick Gravgaard) make alignment a view.** The file holds tabs; the
   editor computes each column block's width so adjacent lines sharing a tab in a column
   align. The canonical printer never counts spaces to align a comment column or a table:
   it emits a tab, and alignment is the viewer's job, the printer law again. Viewers
   without elastic tabstops (terminals, GitHub) get a spaces spelling as a print profile,
   as glyph-less viewers get the name spelling; the file stays tabs.
3. **Tabs complete the rank literal.** Space = token within a cell, tab = cell boundary,
   newline = row: TSV, and ASCII's US/RS. It closes a real gap: in the `@.` table
   `"circle"⇥[ shape/r dup × π × ]` is a tag cell and a quotation cell whose interior
   spaces are tokens; without tabs a multi-token cell was unsayable. See the ranked
   whitespace ladder in [FON](02.03.03-fon.md#4-ranked-whitespace-arrays-tables-spreadsheets)
   and its code/data table in
   [entries and checks](02.03.08-entries-checks-forcing.md#4-the-whitespace-ladder).

Grammar change: `_NL: /(\r?\n\t*)+/`, indenter `tab_len = 1`.

**S20, done:** tabs are cell boundaries in the grammar
(`frame: _TABS? (cell (_TABS cell)* _TABS?)?`, `cell: item+`); a run of tabs is one
separator and there are no empty cells (write `⟨⟩`). The `@.` row now parses as two cells,
a tag and a quotation. The flat property is stated exactly as the first law has it:
`print ∘ parse` canonicalises arbitrary source, `parse ∘ print = id` on the canonical
tree; both hold, 2000 examples each. **Not yet:** blank lines as a higher axis (the `_NL`
regex merges them; the indenter needs the merge): the next grammar step. The decision
whether rank lives in data and section in code is made by saturation after the parse, not
by the parser.

**The cost, stated plainly.** Terminals and GitHub render a tab as eight spaces and know
nothing of elastic tabstops; the editors that do are plugins on Gravgaard's list, not the
mainstream. That is an argument that mainstream editors are worse than they should be, not
an argument against tabs. Elastic tabstops have been described since 2006, are trivial to
implement, and end the tabs-versus-spaces war, which exists only because editors made the
file carry the alignment. FPL does not carry other people's tooling debt in its files: the
file is tabs, alignment is the viewer's job, and a viewer that cannot do it gets the spaces
print profile as an accommodation, not as the canon.

## 8. No Postel

The first attempt was the robustness principle: read four leading spaces as one tab, emit
only tabs, normalise through a logged word `postel : text -- text`. It was retracted in two
steps the same day.

- **Retracted into a word.** The robustness principle is a trap the IETF has since
  withdrawn (RFC 9413, Thomson and Schinazi, 2023): tolerance in receivers ossifies and
  diverges, because every deviation silently accepted becomes something a sender
  somewhere relies on. HTML is the cautionary tale and HTML5 the remedy: it *specified*
  error recovery exactly, so tolerance is deterministic and identical everywhere. The
  failure is unspecified, invisible tolerance, not tolerance. Without the strictness rule,
  `a / ␣␣␣␣b` parsed silently as two sibling lines, because `%ignore` flattens spaces.
- **Superseded the same hour: no Postel at all.** With fewer than a thousand lines of FPL
  written there is nothing to be compatible with, and that is the only moment this is
  free. The `postel` word and the tolerant mode are removed. Leading spaces outside
  brackets are an error, full stop (`line 2: indentation must be tabs`); the canonical
  printer is the only normaliser and it runs on trees, not text. Inside `[ ] ( ) ⟨ ⟩`
  leading whitespace is layout and left alone; a block comment removed at column 0 leaves
  a marker so its gap is not read as indentation. Harness: `strict_indentation`, no
  `tolerant` parameter.

The RFC 9413 analysis stands as the reason. Its companion, RFC 8701 GREASE (send
valid-but-unused variations so receivers never learn to assume their absence), stands as
the schema-evolution rule for `fpl://`: an unknown key in a `{ }` record is must-ignore
or must-understand per field, and an unknown must-understand field is a hole, neither
silent tolerance nor a crash (see
[FON, parser dramas](02.03.03-fon.md#6-pre-empting-the-parser-dramas)).

## 9. Multiline strings are free; incidental indentation

Because the pre-lexer stashes a string before the indenter sees a newline, a string's
interior may contain anything — newlines, tabs, `[`, `⍝` — and named closers cover a string
containing its own closer. The one decision this hides is taken as Java's text blocks (JEP
378) and Rust's `indoc` take it: a multiline string opened on a line at block depth *d* has
*d* leading tabs stripped from each continuation line (incidental indentation), and the
printer restores them, so the printer law holds and string content stays free of layout.
Raw `「 」` strings and named-closer strings keep everything.

```
greet : -- s
	“Dag Ada,
	dit is de tweede regel.”	⍝ interior: Dag Ada,⏎dit is de tweede regel.
	「raw
	keeps its tab」	⍝ interior: raw⏎⇥keeps its tab
```

## 10. No `;`: the newline is Go's semicolon, indentation a better one

The claim that `;` helps error reporting is right for a precise reason: an explicit
terminator is a *synchronisation point*. After an error the parser skips to the next `;`
(panic-mode recovery) and the error stays localised between two. Without one, something
else must serve (JavaScript's ASI hazards are the anti-example). Here the terminator
exists, invisibly: Go inserts `;` at every newline, and the line is the statement. The
off-side rule improves on `;` because `;` is flat and indentation is hierarchical:
resynchronise at the next DEDENT, skipping a whole failed body (why Python's
IndentationError localises so well). The semantic role of `;` — sequencing statements as
against expressions — has no object in a concatenative language: sequencing is
juxtaposition.

The one real gap is brackets spanning lines (multi-line quotations): a forgotten `]`
swallows the rest of the file, and "unclosed at EOF" is the worst message there is. Fix,
as in Haskell's layout `parse-error(t)` rule and Rust's parser: **a bracket opened on a
line at depth d may not stay open once a later line dedents below d**; the error is
reported there and names the opener. Implemented in the pre-lexer:

```
f : a -- b
	x [ 1 2
		3 4
g : c -- d	⍝ → line 4: dedent below line 2, but its [ is still open
```

Not for the braced data profile (no lines, only depth; a simdjson-style "first structural
error at position n" suffices for machine data, see the braced spelling in
[FON](02.03.03-fon.md#7-layout-spellings-indented-and-braced)), and the structural editor
removes the class outright by never producing unbalanced text. (`;` was later reclaimed as
the comment glyph, see [spellings and comments](02.03.06-spellings-and-comments.md#5-comments-s33-s48).)

## 11. No Python colon

Python's trailing `:` is an *opener*: it announces a block for the reader and lets a plain
editor auto-indent on Enter (and permits one-line `if x: y`). Here the head line is the
*closer* of its block — children first, head last, the invisible `]` — so an opener marker
would mark something the evaluation order does not have; the indentation opens the block,
and that is Dyck, unambiguous. The one-line form exists already: `[ ]`, the braced
spelling, sugar in both directions. What the colon really provides — a prediction that a
block follows, so the editor indents — the language provides better without punctuation:
**the head knows.** `if`, `each`, `repeat`, `select`, `agenda` expect quotations by their
effect lines; an editor that knows the dictionary sees an unsaturated head and indents.
Python's `:` is the user telling the editor what the language already knows; here the
effect line is that information, and in a structural editor one presses Tab. The closer
side, where Ada's argument lived, is already the opt-in `end name`.
