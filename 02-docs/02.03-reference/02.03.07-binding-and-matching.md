# 02.03.07 2026-09-28 — Binding and matching

Decisions S34 to S43, split out of the [FON](02.03.03-fon.md) decision log. They answer
one question from several sides: how does a postfix, concatenative language get names,
destructuring, defaults and grammars without adding mechanisms? The answer each time is
that the mechanism already exists in the [surface grammar](02.03.02-grammar.md) (a head
line, child lines as quotations, binders `→x`, the inert `( )` group) or in the
[substrate](../02.04-explanation/02.04.04-substrate.md) (`space`, `unify`, failure as
`+fail`, records as directories). The revisions S45 and S49 ([entries, checks and
forcing](02.03.08-entries-checks-forcing.md)) correct some spellings here; where they do,
the correction is flagged.

## 1. Lambdas (S34) and positional arguments (S36)

**S34 — lambdas are quotations that begin with binders.** A quotation is already a closure
(lexical capture: `→base` above, `base` inside). The named parameter exists too: `→x`. So
`[ →y →x  x y - ]` is Smalltalk's `[:x :y | x - y ]`, Ruby's `{ |x, y| x - y }`, Factor's
`[| x y | … ]` — no new syntax. Binders pop from the top, so the order is the reverse of
Smalltalk's, and the quotation's effect line follows from them. Capture per reference as
the cell decision already has it: `x` a snapshot at construction, `$x` the cell.
Smalltalk's `^` (non-local return) is not sugar but `shift` within the frame, which
exists. Point-free stays the default; the lambda is the exit when juggling stops reading.

**S36 — positional arguments `$0 … $n`.** A middle rung between point-free and named
binders, and Swift's exactly (`{ $0 - $1 }`): in a quotation, `$n` is the *n-th argument at
entry* — implicit binders, `$0` the first pushed, arity the highest index plus one,
inferred — so `[ $0 $1 - ]` ≡ `[ →y →x  x y - ]`. Never "the n-th stack position now"
(Forth's `pick`, which shifts under every push). No collision with `$x`: a name cannot
begin with a digit, so `$`+number and `$`+name are distinct token shapes, and the meaning
is the same `$` — the value of a reference inserted here; only the referent differs (an
argument slot, a cell). (S49 item 4 adds the third `$`, `$code:digest`, told apart by the
colon.) Not adopted, because each exists already: `$@` is point-free (a quotation without
`$n` *is* all its arguments); `$?` is `try`'s Option (failure is control, not data); `$0`
as the program/recursion (shell) or the whole record (awk) — `recur` is the word and the
row is the record; `$$` (the pid) is recorded as a *possibility*, not adopted: the
identity of the current frame — the cell reached by `..` from inside — would be spelled
`$..` under the existing rules (`$` on the parent path), giving a frame its own `$` for
supervision, restart and `fpl://` addressing without a new sigil; it becomes a decision
when a program asks for it. Three rungs of explicitness: point-free → `$n` → `→x`.

## 2. Pattern matching (S35, S37, S38)

**S35 — pattern matching, made hard.** The pieces existed (`agenda`/`@.` pattern-keyed,
`_` wildcard, constructors run backwards, clauses as paths `f/1`, `unify` in `logic/`);
this joins them.

- A pattern is a constructor expression read backwards: `( circle r )` as a pattern runs
  `circle` inverse — it matches what `circle` built and binds `r`. Bare names in a pattern
  *bind* (Haskell); `_` matches anything; literals match by equality; `$x` in a pattern
  matches the *current value* of x (Elixir's `^x`).
- Guards are ascriptions in the pattern: `( circle r ∈ pos )` — refinements as guards, one
  mechanism, no `when`. (Respelled `( circle r: pos )` by S49, where `∈` is withdrawn.)
- `match` is the head word; its rows are a rank-2 literal with tab cells: pattern, body.
  First match wins (Haskell, Prolog); overlapping patterns are allowed and order is
  meaning; no catch-all → the `match` is partial and gets `+fail` inferred (Haskell's
  incomplete-patterns warning becomes an effect).
- Overloading on types is matching on types: `( _ ∈ Int )`. Static where the types are
  known, dynamic dispatch with `+fail` declared elsewhere.
- `agenda`/`@.` becomes `match` — the same thing once the agenda is pattern-keyed; `@.`
  stays as the glyph view.

```
area : shape -- n
	match
		( circle r )	r dup times π times
		( rect w h )	w h times
		_	sorry
```

Two parsimony steps. **Taken:** no `[ ]` around bodies — `match` is a head word and a head
word receives its child lines as quotations already (the rule `if` and `each` use), so a
row is pattern cell, tab, body cell. **On the table, S37:** no `match` at all — the pattern
in the head, Haskell's `area (Circle r) = …` with `:` as the clause marker it already is:

```
area : ( circle r ) -- n
	r dup times π times
area : ( rect w h ) -- n
	w h times
```

Each head is a clause, `area/1` falls out as a path, a clause contract hangs under its own
head, `[or] fold` over the heads is the logic seam; zero new words. Its price is
principled: names in the effect line would become binders, and today `mean : xs -- m` binds
nothing — `xs` is type and documentation and the body is point-free. The exit is a rule,
not a heuristic: only a *group* `( … )` in the head is a pattern and binds; a bare name
stays type-side. An asymmetry one has to want; recommended only if the Haskell form is the
goal.

**S38 — what a pattern may be: the inverse of an injective constructor** (prompted by Agda
mixfix and regular-expression heads). The recalled form `String* _f_ (String, Int)*` is
XDuce/CDuce's regular expression pattern matching (Hosoya and Pierce; kin: Raku slurpies,
Egison sequence patterns, `syntax-rules` ellipses); Agda's mixfix is another thing,
underscores as argument positions in a name. Both fall to rules already in force: a postfix
language has no fixity (application is juxtaposition, one order is the parsimony; and `_`
is the hole), and a regular language over the stack is variadic arity, refused because
saturation needs static arity — XDuce's own linearity-and-unambiguity discipline is exactly
the heuristic layer LangSec forbids here. The useful part — `(x:xs)`, Prolog's `[H|T]` —
comes free from S35: **a pattern is the inverse of an injective constructor.** `cons` (one
element, one rest) is injective, so `( cons x xs )` binds head and rest unambiguously;
`snoc` for the last element; `pair` and record constructors likewise. Catenation `,` is not
injective (where to split?) and is therefore no pattern unless one side has fixed length —
one decidable rule, and it names exactly where XDuce's ambiguity begins. Sequences are
matched recursively, as in Haskell and Prolog; a sequence queried *as a whole* is
`select`/`find` over the array, where a regex belongs as a value, not a head. No new prefix
(`…xs` was considered and refused: an eighth, and the affix discipline says seven, see
[spellings](02.03.06-spellings-and-comments.md#2-symbol-and--for-content-s29-revising-s16)), no star, no
linearity heuristic.

```
sum : ( cons x xs ) -- n	; S37 form for illustration; equally a match row
	xs sum x +
sum : ⟨⟩ -- n
	0
```

## 3. Variadics, keyword arguments, defaults and currying (S39)

One mechanism covers all four.

| Python | FPL | why it coincides |
| --- | --- | --- |
| `*args` | an array: `a b c \| f` or `⟨ a b c ⟩ f` | no variadic *head*; "variadic `+` is a fold over a strand" — the call site looks variadic, the arity is one |
| `**kwargs` | a record: `xs { sep “, ” } join` | the `{ }` dict pair, keys literal, values evaluated; the record is one argument at a fixed position |
| defaults | in the effect line: `join : xs { sep “ ” end newline } -- s` | the head declares the option record *with* values; the elaborator unions the caller's record over it |
| forwarding / overriding | `union`, right-biased | records are a **monoid** under union with `{ }` as unit — and "later wins" is `bind`'s law (later shadows earlier): defaults-then-caller is log order |

Why `if kwargs is None: kwargs = {}` disappears: Python needs it because `None` is the unit
of nothing; `{ }` *is* the unit of union, so forwarding is passing the record, overriding is
union, and the empty call is a no-op. Why the mutable-default bug disappears: Python's
`def f(x=[])` fails because the default is evaluated once *and* mutable; ours is evaluated
once, at definition, and that is correct because arrays are values (the K rule). A per-call
default (Python's `None`-sentinel trick) is written `{ end _ }`: `_` in a data position is
*absent* ([FON, the absent cell](02.03.03-fon.md#4-ranked-whitespace-arrays-tables-spreadsheets)),
and the body decides with `unwrap`/`or` — an honest sentinel.

With currying: `{ sep “, ” } [join] curry` saturates and closes the option slot. To *narrow*
defaults while leaving them open, `[join] { sep “, ” } with` — `with : q opts -- q'` is
curry-with-union: `functools.partial` made composable, every `with` unions, the final call
unions last. Repeated application with no `if`.

Two stances that keep it parsimonious: (1) **defaults are keyword-only** — Python's
`def f(a, b=1)` makes the arity 1-or-2, variadic, refused; positional defaults go in the
record. (2) **Unknown keys are an error**: the option record has a row type from the head, a
keyword typo is an elaboration error (Python's `TypeError`, statically), and
must-understand/must-ignore per field is the GREASE rule of the
[grammar](02.03.02-grammar.md#8-no-postel). No `*`, no `**`, no `=` in the head: an array, a
record, `union`, `with`.

**Python's surface on a static core.** Three ways to pull from a record or list, none
touching arity. (1) Bind in the head, by S37's rule that a *group* in the head is a pattern:
`join : xs { sep “ ” end newline } -- s` binds `sep` and `end` in the body, the pattern's
values being the defaults (missing keys take the pattern's value: S39's union) — `def
join(xs, *, sep=" ", end="\n")`, with the record as one argument. (2) Pull by path in the
body: a record is a directory, so `opts/sep` names the entry, the mechanism of `mean/doc`.
(3) Lists: `( cons x xs )` as a pattern (S38), or the array whole with `first`/`skip`;
variadic at the call site is the strand, `1 2 3 | sum`. Above all three, a print profile
([spellings](02.03.06-spellings-and-comments.md)) may show `{ sep “, ” }` as `sep=", "`:
the same ABT with Python's face. Core: one array, one record, fixed arity; sugar in the
pattern and the printer, never in the semantics.

## 4. ABC, verified: holes as completion

(Meertens, Pemberton and Van Rossum, *The ABC Structure Editor*, CWI CS-R9256, 1992.) The
editor shows holes as `?`; typing `P` suggests `P?UT ? IN ?`, `WH?ILE ?: ?`, and it works
for user-defined commands too, `G?ET LIMITS FOR ? AND ?` — mixfix with holes as completion,
formalised as keyword grammars (Geurts and Meertens 1978) with CAPITALS as the lexical
class separating skeleton from argument. Four things land here: `?` was their hole (we
moved `?` to `unwrap` and made `_` the hole — a deliberate break, now with a named
ancestor); brackets can only be entered in pairs and indentation counts as an implicit pair
— "it is impossible to create a bracket mismatch": Dyck-only editing, implemented in 1984;
the *blind typist's rule* — what templates produce must be typeable character by character
with the same result — is the printer law seen from the editor; and their retrospective
regret, "ideally the whole editor should be parametrised with a syntax and no more", is
what the structural editor promises (see [UI](../02.04-explanation/02.04.06-ui.md)). Why
their mixfix is not a core form here: it rests on the CAPITALS class and on LL(1) guessing.
Here the skeleton `PUT ? IN ?` is a template over the postfix ABT `x y put` — a view with
named slots, a profile `under abc` — and completion comes not from a guess but from the
effect line: type `d`, and the dictionary says two quotations follow.

**The editor, better than ABC's for a precise reason: ABC predicted syntax, this predicts
semantics.** The term is not LALR (a parser class) but *stack-effect inference* (Factor,
Cat, Kitten), more broadly type-directed completion (Hazel's typed holes, Agda's `auto`,
Hoogle). At every point in a line the elaborator knows the frame's running arity balance —
what is on the stack, with types — hence which words fit now, and at a `?` goal the
expected type, hence the candidates. At `xs` the completion is `sum`, `first`, `shape`,
`[f] each`; at `d` "two quotations follow". The LSP is the elaborator as a service:
completion by effect line, hover = the stack after this token (Factor's inference display),
diagnostics = unsaturated frames and `+fail` without a catch-all. Structural editing gets
easier than ABC's, not harder: Dyck-only (pairs only), tabs as blocks, elastic tabstops
([grammar](02.03.02-grammar.md#7-indentation-is-tabs-alignment-is-elastic-tabstops-decided-2026-09-27)),
and the blind typist's rule holds because the tokeniser is decidable per character
(whitespace). ABC's regret becomes: parametrised with a *dictionary* and no more. The
limit, stated: the balance is static only where arity is; behind a dynamic dispatch the
editor shows `+fail`, not a guess.

## 5. Grammars are `match` in a `space` (S41)

(Prompted by SNOBOL, Icon and Raku grammars.) S38's "catenation is not a pattern" holds
*outside* a `space`, where `match` is deterministic. *Inside* one, a non-injective pattern
is not a problem but a **relation with several solutions**: `( , a b )` as a pattern yields
every split, one per backtrack — SNOBOL's `ARB`, Icon's generators, Prolog's DCG (a grammar
as relations over lists). Raku's `token` (ratchet) is `match` outside a space, PEG's
ordered choice; Raku's `rule`/`regex`, SNOBOL and Icon's `every` are `match` inside one;
packrat memoisation is a solver strategy in the penumbra, invisible under the semantics.
Two consequences: every dialect pair gets its parser this way — `⟪tei … tei⟫`'s `tei/read`
is a `match` grammar in FPL, no Lark — and FPL's own syntax stays the LangSec recogniser,
total and linear: grammars-as-`match` are for what stands *inside* a pair, never for the
pair. Naive backtracking's worst case is the price of `space`; `n space` (bounded) is the
brake that already exists. Dialect blocks in prose are covered by
[FML](02.03.04-fml.md#2-polarity-flipped-and-literate-programming-falls-out).

**The tie to logic programming is the whole gain.** Matching is one-way unification —
pattern variables bind, value variables do not — the same algorithm as `unify`. Outside a
`space`: first match, deterministic, `+fail`. Inside a `space`, with `fresh` variables:
two-way, all solutions, backtracking — and the `match` rows are then Prolog clauses
literally, `[or] fold` is the logic seam's disjunction, and `f/1` is the path to clause 1.
One mechanism, two seams; the enclosing `space` decides which you get. It does not connect
to logic programming; it *is* it.

## 6. `let`, `where`, and types on values (S42, S43)

Both exist already, in the shape `match` has. `let x = … in body` is `… →x body`: the
mortal binder, scoped to the rest of the block. `where` is **the child block**: children
first, head last, so the details stand *under* the expression that uses them — Haskell's
readability argument for `where`, and this language's evaluation order. `hypot : a b -- c`
/ `+ sqrt` / `a a times` / `b b times` (children push, head consumes): point-free `where`;
names, if wanted, are bound by the head (`→b2 →a2`), and mostly they are not wanted.
`match`, `where`, `if`, `each`: one form, head above, parts beneath.

**S42, the rule this forces:** a binder in a child line does not leak into the head —
children are quotations (the block is the invisible `[ ]`) and a `→x` in a quotation is
local to it; otherwise mortality is false and scope is not lexical. Push a value up, or
bind a name in the head.

**S43, types on values:** not needed by default — elaboration is bidirectional, the effect
line checks, the body synthesises. (The one ascription word `∈` proposed here is withdrawn
by S49: the typing colon `name: Type` replaces it, see
[entries, checks and forcing](02.03.08-entries-checks-forcing.md#6-the-head-forces-s49).)

Open detail: destructuring bind outside `match`, `→( circle r )` — the `→` prefix on a group
instead of a name. Tokeniser: `→` and the group are two tokens; the elaborator joins them;
grammar unchanged. Owed to the harness: `match` rows as (pattern, body) cells,
exhaustiveness → `+fail`, and the inverse-constructor reading of `( )` in pattern position
(the same inert reading the data profile gives `( )`, then run backwards).
