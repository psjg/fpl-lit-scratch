# 02.03.03 2026-09-27 — FON: FPL Object Notation

FON was proposed on 2026-09-27 as one question: given S-expressions through `( )`, JSON,
XML, YAML and CSV/TSV as embeddings, is FPL homoiconic the Lisp way, and can code be
dumped as data? The answer is that FON is the **literal subset** of the
[surface grammar](02.03.02-grammar.md) plus one pair (`{ }`) and one prefix. The codec
that reads and writes it, without elaborating, is the boundary pass
[FON](../../01-bootstrap/01.01-boundary/01.01.02-fon.md); its text-out sibling is
[render](../../01-bootstrap/01.01-boundary/01.01.04-render.md).

The companion profile for prose is [FML](02.03.04-fml.md), which treats FON's tagged
tuples as its semantic layer. The substrate behind references, masks and capabilities is
in [substrate](../02.04-explanation/02.04.04-substrate.md); the reasons for the glyph and
spelling choices are in [syntax rationale](../02.04-explanation/02.04.05-syntax-rationale.md).

## 1. Homoiconic, the Lisp way

The reader's output is already a literal in the language's own notation. Draft 1's `node`
yields *children-quotations, then the head line*; dumped and read back with the prototype
grammar:

```
shortest-paths : D -- D
	dup ⍴ ⊑ 2 log ⌈ →k
	k ⍟
		dup ⌊.+
```

```
[ [ dup ⍴ ⊑ 2 log ⌈ →k ] [ [ dup ⌊.+ ] k ⍟ ] shortest-paths : D -- D ]
```

The dump parses back as FPL (one line, one quotation) and prints canonically to the same
text. Differences from Lisp: post-order (head last, a reversed S-expression, because the
language is postfix), and the quote is `[ ]`: mention-is-use makes bare `dup` a call and
`[ dup ]` the datum; Lisp's quote is `[`. Not the Tcl/Icon way (code as string), though
that exists too: `“1 2 +” read tree !`. Dumping code as FON is `read tree`; nothing new is
needed for it.

## 2. FON is the literal subset, plus one pair and one prefix

| kind | FON | JSON | XML / SXML | YAML | CSV / TSV |
| --- | --- | --- | --- | --- | --- |
| number, string | `36`, `“Ada”`, `「raw」` | same | text | same | cell |
| list | `⟨ 1 2 3 ⟩` | array | children | `- 1` | row |
| record | `{ name “Ada” age 36 }`: `{ }` is free and becomes the dict pair, keys literal, values evaluated | object | attributes | `name: Ada` | column headers |
| code | `[ … ]` | none | none | none | none |
| element | `( p { class “x” } “text” ( em “y” ) )`: literally SXML; `( )` rotates it into a constructor call | none | `<p class="x">` | none | none |
| absent | mask (`Option`) | `null` | none | `~` | empty cell |
| reference | `name` (petname), `$name` (identity), `&hash` (content; the spelling started as `#hash`, see S29) | none | `id`, `href` | anchors `&` and `*` | none |

Observations:

- **YAML is `{ }` with the off-side rule**: `{` on a head line, entries as indented lines
  `name “Ada”`. As readable as YAML, Dyck-safe: YAML's `no` → `false` and indentation
  accidents cannot occur, because keys are literal and blocks are counted.
- **TSV is native**: a noun-only block with space = column and newline = row is the
  rank-2 literal already in the design. CSV (commas, quoting) is a pair, `⟪csv … csv⟫`,
  reading to the same rank-2 array, or to a q-style table (a dict of columns), the better
  form for `select`.
- **XML is SXML is `( )`**: SXML's `(p (@ (class "x")) "text" (em "y"))` is FON with `{ }`
  for the attribute list; in the data profile `( )` reads as a tagged tuple; the rotation
  into a constructor call happens only in a later, capability-gated build step (section
  6). Overlapping markup (TEI) stays milestones and standoff, as decided in
  [FML](02.03.04-fml.md#7-not-yet).
- **Content references are the missing prefix.** The substrate's three reference kinds
  (petname as a bare name, identity as `$`, content as a hash) are all needed to dump the
  store, see [substrate](../02.04-explanation/02.04.04-substrate.md). The prefix is `&`
  (S29).

## 3. Observation: one grammar, three profiles

FON-data (section 9) is the literal subset without off-side blocks, islands, dialect pairs
and comments. It keeps the Dyck principle intact, so it shares the canonical printer, and
it is what one sends over a line when sending text at all. Code is the full
[grammar](02.03.02-grammar.md); prose is [FML](02.03.04-fml.md). Decision S21.

## 4. Ranked whitespace: arrays, tables, spreadsheets

With tabs as cell boundaries the shape of a literal is in its whitespace, so higher ranks
need no reshape verb after the fact (APL's `2 3⍴…`, `,:`, `⍪` exist because the notation
had one dimension, the space): space = tokens within a cell, tab = cell, newline = row,
blank line = next axis, two blank lines = the axis after — ASCII's US/RS/GS/FS, four
levels, extensible by counting. Unequal rows give a ragged list (K), not a rectangle;
rectangularity is a type claim the elaborator checks, not a consequence of the notation.
The code-side reading of the same ladder is in
[entries and checks](02.03.08-entries-checks-forcing.md#4-the-whitespace-ladder).

**Tables.** A tab block with a header row of names is a q table (a dict of columns): the
pandas DataFrame, the SQL relation and the Markdown table are three surfaces of that one
value; `select` is native, `⟪sql … sql⟫` and `⟪md … md⟫` are dialects reading to it.
Markdown's pipes collide with the bar, so they live only inside their pair. (FML takes the
same tab block as its table, [F10](02.03.04-fml.md#3-decisions-f1-f20).)

**Spreadsheets fall out.** A spreadsheet is a rank-2 literal whose cells are islands —
`⟨$b2 $c2 +⟩` for `=B2+C2` — with `$` making each cell a view that recomputes on the log
clock, elastic tabstops drawing the grid, paths as named ranges, `select` as Power Query
and the log as undo. The rank literal plus two existing mechanisms; Excel minus the
application.

**Canon Cat, Lisa.** Raskin's Cat: one continuous text as the whole interface, leap keys
to move, and a *calc* command evaluating an expression in place — text as carrier with
`⟨ ⟩` islands, literally. The Lisa: document-centric rather than application-centric — the
rule that a file picks its interpreter by its first character, and the image as the
system. Both lacked the log and `$`: the reactivity that would have turned the Cat's
one-shot calc into a living document. See [UI](../02.04-explanation/02.04.06-ui.md).

**Consequences of tabs-as-cells for FON.**

1. The table literal *is* FON: a tab block with a header row of names is the q table, and
   since a cell may hold several tokens it may hold a nested FON value (`{ … }`, `⟨ … ⟩`)
   — TSV with structured cells reconciles JSON's array-of-objects with CSV's flatness;
   higher rank (JSON's nested arrays) is blank-line rank once that reaches the grammar.
2. The FON of a spreadsheet is a tab block of islands and `$` references, so the dump of a
   view table is literally the spreadsheet file; one printer, no second serialisation.
3. **The absent cell, correcting S17.** `⟨⟩` is the empty *list*, not absence. An empty TSV
   cell and JSON `null` are *absent* — masked, per the failure decision — and the glyph for
   that exists: `_` means "unspecified here": a hole as a term, a wildcard as a pattern, and
   in a data position a masked element. S17 becomes: JSON `null` and the empty cell read as
   `_`, and `_` in a data position is the mask. One glyph, one meaning, third position.

## 5. Parsing speed, and the wire

**Why JSON parses at 2+ GB/s and XML an order of magnitude slower.** simdjson (Langdale
and Lemire) is two-stage: stage 1 finds the structural bytes `{}[]:,"` with SIMD masks,
branch-free, correcting for strings by a prefix-XOR over quote bits; stage 2 builds a tape.
It works because JSON's structure is a handful of fixed bytes recognisable without
context. XML fails on every point: end tags are the copy language (Type-1), entities are
macro expansion (billion laughs), DTDs, namespaces, mixed content, encoding declarations —
context-sensitive on every byte.

**Where FON stands.** Better than JSON on two counts, worse on one, equal otherwise.

- Paired, distinct delimiters with no escapes: all structure is `[ ] ( ) ⟨ ⟩ { } “ ” 「 」
  ⟦ ⟧`, self-delimiting and context-free to recognise. Nested strings need a counter
  rather than JSON's toggle; a prefix sum over ±1 masks is equally branch-free. Being
  Dyck, a value can be skipped by counting alone — simdjson's On-Demand (lazy) mode is the
  normal state here, the same property that lets dialects exist.
- Unquoted keys and whitespace as cell boundary: fewer bytes than JSON; tokenising is
  "find the whitespace bytes".
- The off-side rule is the apparent cost: indentation needs a stack. The data profile
  excludes it (and see the correction in section 7: with tabs the cost is nil).
- Unicode delimiters are three bytes: SIMD matching of multi-byte patterns works (simdjson
  validates UTF-8 at full speed) but is less clean than single bytes. ASCII has only three
  distinct pairs (`[] () {}`), so a pure-ASCII profile would have to escape strings again —
  that is JSON. Keep the Unicode pairs; whoever wants faster wants binary. (The ASCII
  digraph spelling is on the [spellings](02.03.06-spellings-and-comments.md#1-ascii-spelling-s28)
  page.)

**The fastest parser is no parser.** Over the wire: zero-copy (Cap'n Proto/FlatBuffers-style
in-place access), not tagged length-prefixed formats (CBOR, MessagePack), which still
decode. The substrate already has two fitting zero-copy forms: the content-addressed ABT
nodes of the store (code and records: the wire is the store) and **Arrow** for tables —
columnar, and Arrow's validity bitmaps are literally the masked arrays. Three layers: text
FON for people and models; simdjson-class parsing of text FON-data; Arrow and store nodes
on the wire.

**Grammar change?** No; a *profile*: **FON-data** (decision S21).

## 6. Pre-empting the parser dramas

The incidents of the last decade fall into a few classes, most already named by LangSec
(Sassaman, Patterson, Bratus): *recognise the input fully, with the weakest sufficient
Chomsky class, before processing it*; "shotgun parsing" is the anti-pattern. The
[layer table](02.03.02-grammar.md#1-layers-and-what-lives-where) is therefore the security
design, not a curiosity.

| class | examples | prevention in FON |
| --- | --- | --- |
| Parser differentials — two parsers read the same bytes differently | JSON duplicate keys (first vs last wins → auth bypass), `1e1000`, big integers losing precision, `-0`, `"1"` vs `1`, lenient trailing commas | one canonical form and `parse ∘ print = id` as law; a `{ }` with a repeated key is a parse error, not a policy; numbers canonically spelled (no `+`, no leading zeros, no textual NaN/inf) and delivered **exact**; conversion to float is a separate step under the substrate's rounding model, never silent in the reader |
| Code in data — deserialisation RCE | YAML `!!python/object` (Rails 2013, SnakeYAML), Java serialisation gadgets, pickle | the **FON-data profile is inert**: the reader never evaluates, resolves names or constructs typed objects. Names are symbols; `[ ]` yields a `Code` value (level 1, not run); `{ }` a dict with literal keys; `( )` yields a *tagged tuple*, not a constructor call: reading XML is not building it; building is a second, capability-gated word after validation |
| Expansion bombs | XML billion laughs, entity expansion, XXE (SSRF, file disclosure) | no macros, entities, includes or followed references in the data profile; `&hash` and `$` references are *values* the reader does not follow; following is a capability of the consumer |
| Resource DoS | deep nesting (stack overflow), huge tokens, hash flooding on keys | bounds are part of the profile, not the implementation: maximum depth, token length, input size declared; a bounded Dyck counter is effectively regular; recognition is total and linear (LALR + counting, no backtracking, no `+div`); keys are symbols interned by identity |
| Signature wrapping | XML Signature (bytes signed of a structure with several parse trees), non-canonical CBOR | signatures are over the **tree** (content addressing hashes the ABT, not bytes); two byte forms with one tree hash equal; where bytes must be signed the printer law gives one canonical byte form |
| Encoding confusion | overlong UTF-8, BOM tricks, replacement characters set differently by two parsers | UTF-8 only, validated first; invalid UTF-8 is a rejection, never `U+FFFD` — replacement is itself a differential |
| Binary lengths | length-prefix bombs, out-of-bounds under zero-copy (Cap'n Proto's own security notes) | text FON declares no lengths to trust; the zero-copy wire format validates bounded lengths as a separate recognition step before any access — LangSec's rule again, for bytes |
| Unknown fields | silent ignore (ossification) or crash | must-ignore / must-understand per field; an unknown must-understand field is a hole (P2) |

The principle in one sentence: **the recogniser is a separate, total, linear, specified
function from bytes to tree, and everything else — evaluating, following, building,
tolerating — is a separate word behind a capability.** LangSec, the retracted robustness
principle ([grammar, no Postel](02.03.02-grammar.md#8-no-postel)) and the zone mechanism of
the [substrate](../02.04-explanation/02.04.04-substrate.md) in one, which is why these
classes need not be patched one by one. Decision S22 (the data profile is inert; `( )`
reads as a tagged tuple).

## 7. Layout spellings: indented and braced

**The one disadvantage, and the serde claim.** The one count on which FON looked worse than
JSON is the off-side rule: indentation needs a stack. Corrected: the disadvantage is nil.
The indenter already does what BCPL/C made visible: it emits `INDENT`/`DEDENT`, invisible
braces, and the parser sees a bracket language (Haskell's layout algorithm, Python's
tokenizer). What looked Type-1 was Python's *width* comparison, the copy-language flavour;
with tabs it is counting — previous depth, new depth, emit the difference in brackets — the
same counter as the Dyck brackets themselves, no extra machine class, linear cost. And the
explicit form already exists: the dump, `[ [ … ] [ [ … ] k ⍟ ] shortest-paths : D -- D ]`,
is the program with the braces made visible, post-order, and parses as FPL. Haskell accepts
both forms interchangeably; here tabs are the source form and the dump the transport form,
each canonical for its kind — so the wire never needs the stack: send the dump.

**Layout spellings (S24).** A third spelling axis beside glyph/name: the same tree written
*indented* (tabs, ranked whitespace) or *braced* (all structure in brackets, whitespace
only token separation in any amount — what JSON is). The printer translates both ways.
Braced: indentation → `[ ]` (the dump, post-order), frames → `|`, and rank-by-whitespace →
**rank by nesting**: the `@.` table becomes
`⟨ ⟨ "circle" [ … ] ⟩ ⟨ "rect" [ … ] ⟩ ⟨ _ [ sorry ] ⟩ ⟩`; tabs and newlines are then mere
spaces. Seen from here the tab/newline rank literal is the indented spelling's sugar for
nested lists. Advantages of braced: the fastest text serde (no lexer stack, pure Dyck,
simdjson-class — FON-data, now for code too); a minified one-line form with the fewest
bytes; far easier constrained decoding for language models (no depth to track); streaming
and append-friendly; no indentation errors. Its one large disadvantage: readability, and
line-based diffs. Hence a rule, not a choice: **indented is the source spelling, braced the
transport and generation spelling**, one canonical form per purpose, the printer law
guaranteeing one tree. FML's tree form `( h1 “x” )` is the same braced spelling for prose
([FML layers](02.03.04-fml.md#1-purpose-and-status)).

**Codebook spelling (S25).** The fourth spelling axis, and the bridge between minified
text and binary: every primitive and every word in scope gets a short code — one byte, or
Huffman by frequency — and the text is the byte stream. Jelly and 05AB1E do exactly this
with their 256-character code pages; there it is hand-built and global, here per
dictionary and per corpus. Three things make it more than golf.

1. The codebook is a value with a content hash: a message names its codebook and the
   receiver must hold it — zstd's pre-shared dictionaries and Ion's symbol tables; here the
   codebook is an ordinary FON value in the store, content-addressed, versioned for free.
2. It is optimal per corpus: a Huffman codebook trained on one's own codebase yields the
   density golf languages pick by hand — "density belongs to the designer" inverted: it
   belongs to the corpus, and a user's own frequent words get short codes.
3. A BPE vocabulary is the same object: a language model's tokenizer is a codebook over
   text, so a FON codebook and a model vocab can be trained jointly — one codebook that is
   both the wire encoding and the model tokenisation. See
   [tokenizer-aware naming](02.03.06-spellings-and-comments.md#3-tokenizer-aware-naming-and-fpl_bpe-s31-s32).

The boundary with "real binary" becomes precise: binary = codebook spelling plus
fixed-width or zero-copy layout for the *values* (numbers, arrays via Arrow); the structure
— brackets, words — is a codebook either way.

**Strictly the best serde?** On every axis at once, nobody: readability and zero-copy
exclude each other. What the best designs do is one data model with an encoding per axis,
Pareto-best per axis. Predecessors, all better than JSON and less known:

| predecessor | what it has | what FON takes |
| --- | --- | --- |
| Amazon Ion | one data model, text and binary encodings, exact decimals, symbol tables, annotations | text/binary over one model; exact numbers in the reader |
| Preserves (Garnock-Jones) | a data model with canonical text *and* canonical binary form, deterministic ordering, hashable | the tree-level canon; deterministic bytes for signatures |
| IPLD (IPFS) | dag-cbor/dag-json with content-hash links as a core value | content hashes as a reference kind in the model |
| Arrow | columnar, zero-copy, validity bitmaps | tables on the wire; the mask as bitmap |
| Cap'n Proto | zero-copy trees, validated bounds | store nodes as the wire form of ABTs |

FON is the intersection of the five in one Dyck grammar. What none of them has: code as
data in the same model (`[ ]`), absence as a first-class glyph (`_`), the three reference
kinds together (name, `$`, `&`), rank by whitespace (TSV native), and an inert profile with
**bounds and threat classes as part of the specification**, not the implementation. Parity,
not a win: raw text parse speed against simdjson (3-byte delimiters, nested-string
counting); small-message compactness against protobuf varints; zero-copy for trees only via
store nodes, never text.

**Missing to compete at all: a schema.** Protobuf's strength is evolution (field numbers,
must-understand). Here the schema is not a separate language but the type — refinements and
the effect line — and the evolution rule is the must-understand/hole rule of section 6.
Make it explicit: **FON-schema = the type language applied to a `{ }`** (S23). The
defensible claim is then not "strictly the best serde" but *the only model in which data,
code, absence, reference and schema share one grammar, with the best existing technique
per encoding*. That claim is structural until benchmarked.

## 8. Blobs, widths and the hardware layer

**Blobs and in-band bases.** ASCII already makes a digit's low nibble its value (`'7' &
0x0F == 7`); the high nibble is a "digit" tag, needed because 0x00–0x1F are controls. Any
text base is a codebook bounded by transport safety: base64 6 bits/byte, Ascii85 6.4,
base122 7 (the practical maximum inside UTF-8); non-ASCII Unicode is worse (11 bits per
16). So text keeps the tag nibble, and FON handles binary two ways: large blobs go **out of
band by content hash** (IPLD's move; the wire is binary anyway), and text-only carriers
use base122 in a `「 」` raw string, no escapes. In the codebook spelling the wish is simply
a table entry: `0` ↦ 0x00.

**Widths, and the hardware layer.** UTF-16 is not fixed width (surrogates, BOM,
endianness); UTF-32 is, at four times the bytes, and at simdjson speeds parsing is
memory-bound, so it loses. Variable width is not the bottleneck: UTF-8 validates in under
one instruction per byte (Keiser and Lemire) because it is self-synchronising —
continuation bytes 0x80–0xBF, lead bytes ≥ 0xC0, ASCII < 0x80 never overlap — which is also
why the 3-byte glyph delimiters are SIMD-findable without colliding with structural ASCII.
(`CHAR_BIT` may differ from 8 in C; POSIX fixes 8; the byte layer says *octet*.) Fixed
width wins where it belongs: the **codebook spelling as the hardware layer** — fixed-width
codes per token, delimiters as reserved codes, nothing to decode; the Dyck recogniser
becomes a counter automaton (one comparator per pair kind, an up/down counter), a direct
FPGA/ASIC design, meeting Fletcher (TU Delft), which couples FPGA accelerators to Arrow's
fixed-width columns. Three widths for three layers: text UTF-8 (people, models); codebook
fixed-width words (hardware); values Arrow columns (zero-copy).

## 9. FON-data in the prototype (S15, S17, S21, S22, S24 implemented)

`fon.py` (now in the repo as [`fon.py`](../../01-bootstrap/fpl/fon.py)) sits beside the
code grammar: a braced, inert data profile with its own Lark grammar, reader, canonical
printer, bounds and property tests. Rung: trede 2 (properties over generated values).

```
start: value*
?value: TOKEN | list | dict | tuple | code
list:  "⟨" value* "⟩"
dict:  "{" (TOKEN value)* "}"          // keys literal tokens (symbols), never evaluated; a repeated key is a parse error
tuple: "(" value* ")"                  // a tagged tuple: the head is data, never called
code:  "[" value* "]"                  // Code, opaque to the data reader
TOKEN: /[^\s\[\]()“”「」⟦⟧⟨⟩{}|⍝]+/
%ignore /\s+/                          // whitespace is token separation only: no off-side rule, no rank
```

Pure Dyck: no off-side rule, islands, dialect pairs or comments; strings by the same
counting pre-lexer (no indentation rule). **The reader is inert**: names are symbols
(`Sym`), `$name` a `Cell` and `&hash` a `Hash` — three reference *values* the reader does
not follow; `[ ]` is `Code` (opaque); `( )` a `Tagged` tuple; `{ }` a dict with literal
keys; numbers exact `Decimal`s in canonical spelling only (`01`, `1e5`, `+1` are parse
errors, never lenient reads or symbols); `_` is `ABSENT`; `true`/`false` words. **Bounds
are parameters of the recogniser**: max depth 64, max token 4096, max input 16 MiB, each a
`Bounds` rejection.

| check | result |
| --- | --- |
| 2000 generated values: `read ∘ write = id`, `write ∘ read` idempotent | holds |
| JSON embedding: `{"name":"Ada","age":36,"langs":["Ada","ML"],"spouse":null,"ok":true,"pt":{"x":1.5,"y":-2}}` | `{ name “Ada” age 36 langs ⟨ “Ada” “ML” ⟩ spouse _ ok true pt { x 1.5 y -2 } }`, reads back equal |
| repeated key `{ a 1 a 2 }` | rejected |
| unclosed, overlapping counted pairs | rejected |
| malformed hash `#zz` | rejected |
| 70-deep nesting | rejected (`Bounds`) |
| `01`, `1e5` | rejected (non-canonical number) |
| `( p { class “x” } “text” ( em “y” ) )` | a `Tagged` tuple tree, nothing called |
| `[ dup ⍴ ⊑ 2 log ⌈ →k ]` | `Code`, nothing run |

Still not implemented: content-hash syntax beyond a hex placeholder (S16, substrate); CSV
as a pair (S18); FON-schema (S23); the indented↔braced translation for *data rank*
(tabs/newlines → nested lists), only the code dump exists; the codebook (S25); mapping to
Arrow and store nodes; UTF-8 validation on bytes (the prototype takes `str`, already
valid); benchmarks.

## 10. Numbers (S27)

Settled: canonical decimal spelling (no `+`, no leading zeros, no exponent), exact decimals
in the reader, `01` and `1e5` parse errors, `∞` and `π` words. Meaning is the substrate's
rounding model (ℤ/2⁶⁴ℤ or refinement; f64 as ℝ with rounding, see
[substrate](../02.04-explanation/02.04.04-substrate.md)) and does not change. The prototype
reader exposed two collisions (hex vs the leading-zero rule; `_` separators vs the hole).
Proposed, not decided:

| question | proposal |
| --- | --- |
| exponent (`1e100` currently unwritable) | allow, one canonical form: mantissa without trailing zeros, lower-case `e`, no `+`: `1e100`, `15e-3`; the printer picks the shorter of positional and exponent forms, positional on ties |
| `36` vs `36.0` | one value, so `36.0` is non-canonical and an error; the type (ℤ, decimal, f64) comes from the type, never from a point in the literal |
| floats: when to round | never in the reader; an f64 context rounds the exact decimal under the rounding model; canonical print of an f64 is the shortest round-tripping decimal (Ryu; JS and Python `repr`), which the decimal reader then reads exactly (superseded by the float decision below) |
| NaN, −0, ±∞ | superseded by the float decision below |
| rationals | `/` is a path, so no `1/3`; `1∕3` with U+2215 division slash, canonically reduced |
| other bases (collision: `0x1F` rejected by the leading-zero rule) | `0x`, `0b`, `0o` as the explicit exception, lower-case, no leading zeros after the prefix; needed for bytes and masks |
| digit separators (collision: `1_000`, `_` is the hole) | none in the canonical form; the canonical text writes full digits with no separator (token-efficient, decided 2026-09-29). Thin spaces are withdrawn as a view by S47 ([every view is injective](02.03.08-entries-checks-forcing.md#5-every-view-is-injective-s47)): `12 483 436` would look like a three-element strand; a view may group digits only injectively, by underlining alternate groups (as the Numderline font does), never by a space-like mark. `_` inside a number token would not collide with the hole (Rust has both) but costs a token per separator |
| binary | Arrow numeric types on the wire; ℤ beyond 64 bits as a bigint buffer; decimals as Arrow `Decimal128`/`Decimal256` |

**Floats settled (2026-09-27): a float literal is its IEEE representation.** No decimal
conversion anywhere in the serde. The format exists and is standard — C99/IEEE 754-2008
hexadecimal floats (`%a`): `0x1.8p3` = 1.5·2³, exact in both directions. Consequences,
replacing two rows of the table:

- Two number kinds, syntactically distinct: exact decimals (`36`, `15e-3`) and IEEE floats
  (`0x1.8p3`, `-0x0p0` for −0, `0x0.0000000000001p-1022` for the smallest subnormal). A
  decimal never silently becomes a float; a float never passes through decimal.
  Decimal→float is an explicit word carrying the rounding model.
- NaN *is* representable, as a float, with sign (and payload, to add): it is a bit pattern;
  the differential risk belonged to decimal parsers guessing, and a typed float spelling
  guesses nothing. `∞` and `-∞` are floats too.
- Canonical: normalised mantissa `0x1.…` without trailing zeros, exponent without `+`;
  `0x1p0` is 1.0. Width (f32/f64) lives in the type; a literal with more mantissa bits than
  the type carries is a type error, not a rounding.
- Decimal display is a view: the printer may show Ryu's shortest round-tripping decimal to
  people; the canonical text is hex.
- The `0x` collision with the leading-zero rule is settled by the same stroke.

Implemented in `fon.py` (`Flt`, `HEXFLT`): 2000 generated values including floats
round-trip exactly; `12.0 → 0x1.8p3`, `-0.0 → -0x0p0`, `0.1 → 0x1.999999999999ap-4`,
`5e-324 → 0x0.0000000000001p-1022`, `max → 0x1.fffffffffffffp1023`, `inf → ∞`,
`-nan → -nan`, each reading back bit-identical.
