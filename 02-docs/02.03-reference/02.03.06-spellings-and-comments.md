# 02.03.06 2026-09-27 — Spellings and comments

Split out of the [FON](02.03.03-fon.md) decision log. It collects the decisions about *how
the same tree is spelled*: S28 (ASCII), S29 (`#symbol`, `&hash`), S31/S32 (names as canon),
S33 and S48 (comments). All of them sit on the printer law of the
[surface grammar](02.03.02-grammar.md#6-the-canonical-printer-and-the-two-laws): one tree,
several print profiles, exactly one canonical form per purpose. The reasoning about
glyph economy is in [syntax rationale](../02.04-explanation/02.04.05-syntax-rationale.md);
the unresolved question of how to spell glyphs where only names can be typed has its own

## 1. ASCII spelling (S28)

A third spelling on the glyph/name axis — glyph, name, **ascii** — for keyboards and
models; same tree, same laws, one more print profile. What it buys: typeability; the best
model spelling (measured: ASCII names are one token, `⟨` two or three); a 7-bit hardware
text layer. Text-parse speed gains are small — single-byte structural masks and no UTF-8
validation, together a minority of simdjson's time — some tens of percent at most, to be
measured; the class jump is the codebook's, not the width's (see
[FON, parsing speed](02.03.03-fon.md#5-parsing-speed-and-the-wire)). The price: ASCII has
three distinct pairs and seven are needed, so digraphs (Dyck intact, still fixed per byte),
never escapes; strings use Rust's levelled `#"…"#` (Lua's `[==[` in ASCII quotes).

| construct | glyph | ASCII |
| --- | --- | --- |
| quotation | `[ ]` | `[ ]` |
| prefix | `( )` | `( )` |
| dict | `{ }` | `{ }` |
| group / list / island | `⟨ ⟩` | `#( )` (`#` before a bracket is unambiguous: a hash reference requires hex) |
| interpolating string | `“ ”` | `"…"` single level; `#"…"#` levelled |
| raw string | `「 」` | `'…'`; `#'…'#` levelled |
| block comment | `⟦ ⟧` | `#| … |#` (Scheme, nesting); superseded by S48 below |
| dialect | `⟪name … name⟫` | `#name( … )name#` |
| line comment | `⍝` | `\\` (Forth); superseded by S33 below |
| modifiers ``´ ` ¨ ˜ ⁼ ˙`` | suffix | separate words on a quotation: `[+] fold`, `[f] each`, `[f] scan`, `swap-args`, `inverse`, `self` |
| `→x` `$x` `&h` `..` `/` | unchanged | unchanged, already ASCII |

Canonical text was proposed to stay Unicode (fewest characters, real pairs); S32 reverses
that for words (section 3). The reader accepts both spellings — not Postel (see
[no Postel](02.03.02-grammar.md#8-no-postel)), since each spelling is itself strictly
canonical and the table is closed.

## 2. `#symbol`, and `&` for content (S29, revising S16)

`#` was serving three roles: content reference (S16), ASCII dispatch before a bracket or
quote (`#(`, `#"`, `#'`, `#|` — Scheme's and Clojure's convention), and now the symbol.
Dispatch and symbol coexist as in Clojure (the next character decides); content and symbol
do not (`#deadbeef` is a name and hex). So the content reference moves to **`&`**, C's and
Rust's address-of — the address of these bytes: `&sha256/…`. The core prefixes become
seven, and no eighth is in sight:

| prefix | meaning | C1 reference kind |
| --- | --- | --- |
| `name` | mention is use: the value now | — |
| `#name` | the symbol itself, as a value | petname |
| `$name` | the cell | identity |
| `&hash` | the content | hash |

(plus `→name` the binder, `../` and `..` the scope paths.) The three reference kinds are
those of the [substrate](../02.04-explanation/02.04.04-substrate.md).

`#` fits the time (the hashtag) where `'symbol` is what people and tokenizers confuse with
quotes and `:symbol` (Ruby, Elixir) collides with the `:` head. What it cleans up matters
more: the examples used strings as names — `"apply" lookup`, `"norm" [ … ] "point" method`
— the confusion Ruby's symbols resolved. Text is `“ ”`; a name is `#name`: `#apply
lookup`, `#norm [ … ] #point method`. In FON-data a bare name already reads as `Sym`; in
code `#name` is the sugar for "this word as a datum", Lisp's `(quote foo)` in one
character. The FML tag is the same `#name`
([FML F4](02.03.04-fml.md#3-decisions-f1-f20)).

## 3. Tokenizer-aware naming, and FPL_BPE (S31, S32)

**Principle (S31).** Choose the name spelling by single-token hits in the large
tokenizers — a tokenizer-aware Huffman, a third criterion beside searchable and typeable,
measurable per word. Measured (85 candidate words, each preceded by a space, cl100k_base
and o200k_base): **74 of 85 are one token in both** — `dup swap drop over rot nip fold scan
each reduce map filter select where group join sort grade first last take range shape rank
split print lookup bind mount mean median sum count min max not and or if else when unless
try unwrap fail hole sorry seam space fresh unify solve splice quote eval apply call self
commute inverse newline tab words doc effect proof history norm log ceil`. Forth, SQL,
Haskell and Rust are in the corpus enough for their verbs to be encoded already.

Exceptions, and what they teach: `tuck` (2), `iota` (2 in o200k), `unquote` (2 — prefer
`splice`); **every affix form costs one extra token** — `->k`, `$cell`, `#print`, `&hash`,
`../io` are 2, `math/mean/doc` 4: the sigil is its own token, the name after it one — the
token price of the prefix decisions, small and known, and one more reason prefixes must
mean something; compound names split on the hyphen (`shortest-paths` 3, `min.plus` 2). The
intuition that a ratio |webtext| / |FPL| near 1 gives good transfer reads as: if FPL's
words share the frequency profile of the corpus languages' verbs, FPL inherits their
tokens — true for the core today.

**FPL_BPE.** Yes, as the codebook ([FON, S25](02.03.03-fon.md#7-layout-spellings-indented-and-braced)),
not a separate thing. Train BPE on the canonical FPL corpus once one exists; the vocabulary
is the codebook spelling and the wire encoding is the token sequence the model reads;
initialise it from the overlap with the large tokenizers so a fine-tuned model learns no
new embeddings for the 74 words it already has. Not yet: there is no FPL corpus (no
frequencies), and the measurement is on OpenAI's tokenizers, not the author's — direction
holds, numbers do not transfer.

**The name spelling is the canon (S32).** Tokenizer-aware naming is pushed as far as it
goes: it becomes standard FPL. Three reasons, two limits.

- *Safe*: a web-scale BPE vocabulary is Zipf's law over human language; the single-token
  words are the words people use most, so optimising for that table optimises for
  familiarity — which is what readability is. Unlike golf, whose code page is Huffman
  against one designer's arbitrary table, this is Huffman against the human prior;
  "density belongs to the designer" dissolves because the designer is the corpus.
- *Robust*: the 74-word core is one token in cl100k and o200k alike, three years apart;
  only rare words differ, and rare words are what the rule avoids.
- *Consequence*: this reverses S28's "canonical text stays Unicode, fewest characters" —
  tokens are the measure, not characters, and names win by 1.5×. **Canonical print = the
  name spelling**: names for words and modifiers (`[+] fold`, `[draw] each`, `swap-args`,
  `inverse`), Unicode pairs for enclosures, sigils as they are. The glyph spelling is the
  expert view, a print profile, not the standard.

Limits: (1) the pairs stay Unicode — Dyck needs seven distinct pairs, ASCII digraphs cost as
many tokens as `⟨` and read worse; the token gain is in the words, not the structure. (2) A
token wins only at equal meaning: if the right word is not a single token, take the
synonym that is (`splice` over `unquote`), never a wrong word for a token. Order: correct →
familiar → one token; the last two coincide, which is the point.

To apply once, as with tabs: the examples are already in the name spelling except the glyph
modifiers — `+´` → `[+] fold`, `draw¨` → `[draw] each`, `-˜` → `swap-args`, `rect⁼` →
`rect inverse`.

## 4. Punctuation words that stay

Consequently: `unwrap` is the canonical spelling and `?` the glyph view — the seam-word
table already said `unwrap` = `?`; S32 makes the name the canon. Likewise `try` = `⍣`. Two
punctuation words stay in the canon, `!` (call) and `,` (catenate): ASCII, one token,
established (Forth/Factor `!`, APL/K `,`) and unambiguous — the boundary: a glyph stays
when it is familiar *and* single-meaning; `?` was neither (Rust's `?`, Agda's hole, prose).
The word-level consequences of "names are canonical" for macros and the head are in
[entries, checks and forcing](02.03.08-entries-checks-forcing.md#6-the-head-forces-s49).

## 5. Comments (S33, S48)

**S33, first form.** The lamp `⍝` fell to S32, and rightly: measured, it costs three
tokens per comment against one for `//`, `;`, `///`, and it carries no prior. `;` was
considered (Lisp's `;` / `;;` / `;;;` levels, Emacs's `^L` pages) and rejected for its
prior: in the languages people and models know, a trailing `;` is a statement terminator,
the opposite of a comment. `//` has one universal prior — *this is a comment*. So: `//`
line comment, `///` doc comment (Rust; attaches to the following definition, the
dictionary's `doc` entry), `⍝` the glyph view; block comments stay the Unicode pair `⟦ ⟧`;
section headers by convention `// ── … ──`; a form feed `^L` is accepted as page whitespace
and, once blank-line rank exists, is the separator one rank above it (space < tab <
newline < blank line < page — ASCII's US/RS/GS/FS ladder, completed). Grammar:
`LCOMMENT.2: /(\/\/|⍝)[^\n]*/`, outranking TOKEN; `a//b` stays one token (a malformed
path), `//` after whitespace is a comment.

**S33, revised the same evening: `;` levels, because the level is an attachment.** `//`
says only "this is a comment"; Lisp's levels say *what it belongs to*, and that is exactly
what serialisable comments needed:

| form | position | attaches to | in the ABT |
| --- | --- | --- | --- |
| `;` | after code on the line | that line's node | trivia-right |
| `;;` | own line, block indentation | the next node in the block | trivia-before; above a definition head, or as the first line of its body, it *is* the `doc` entry |
| `;;;` | own line, column 0 | the enclosing directory | a section heading (Org-like) |
| `;;;;` | column 0 | the file/module | module doc |

Rust's `///` becomes unnecessary: a doc comment is `;;` on a definition, "doc" being the
target rather than a kind of comment. And `;` is a free character where `/` is the path
glyph. The loss is computed, not feared: over the snippet corpus 3166 tokens with `;`
levels against 3164 with `//` (the two are the `;;;` headers) and 3354 with `⍝`. The prior
objection stands as a caveat, not a veto: models and people read `;` comments in Lisp,
assembly and INI; nothing in FPL puts `;` anywhere else. Grammar: `LCOMMENT.2: /(;+|⍝)[^\n]*/`,
`;` self-delimiting (`x; note`); harness: `comments(src)` classifies every comment by level
and position into (line, level, kind, target, text), verified on Draft 2 (the `;; Arithmetic
mean…` line attaches as `doc` to `mean`; see [`trivia.py`](../../01-bootstrap/fpl/trivia.py)).
This answers the "no `;`" decision of the [grammar](02.03.02-grammar.md#10-no--the-newline-is-gos-semicolon-indentation-a-better-one):
`;` is not a terminator, it is the comment glyph.

**Benchmarked, not only counted (2026-09-28).** The loss had been counted (tiktoken), not
measured. Measured with GPT-2 (124M, r50k tokenizer) on CPU — a proxy: it has never seen
FPL and is about 10 bits/token surprised throughout, so this measures differences, not
levels. Total cross-entropy over the snippet corpus, content identical, comment spelling
varied:

| spelling | tokens (r50k) | total bits | bits/token |
| --- | --- | --- | --- |
| `;` levels | 3851 | 39 419 | 10.24 |
| `//` | 3851 | 39 538 | 10.27 |
| `⍝` | 4048 | 39 458 | 9.75 |

The right measure is total bits at equal content, not bits/token: the lamp scores lower
per token only because it costs more tokens (continuation bytes are easy) — the standard
artefact of per-token comparisons across tokenisations. The spread is 0.3 % (120 bits in
39 000), direction `;` < `⍝` < `//`, within the noise of five snippets: the conclusion is
that the choice is loss-free, and the earlier prior objection to `;` finds no support. Not
measured: the author's own tokenizer, a modern model, FPL after fine-tuning; the direction
should hold, the numbers will not. For `⍝` versus `//` the tiktoken count (3 vs 1 in o200k)
remains the relevant fact.

**S48: the block comment is `<!-- … -->`, and it is a node (2026-09-29).** Replaces
`⟦ … ⟧`, which the tokenizers split into single bytes (8 extra tokens for a block on its
own lines, against 3 for `<!-- -->`). Candidates weighed: `[[ ]]` is taken (a quotation in
a quotation — brackets delimit themselves); `(* *)` collides with the prefix form, `{- -}`
with dicts; `/* */` is cheapest (2) but collides with paths; `#| |#` (Common Lisp) and `#[
]#` (Nim) nest by their own precedent and cost 4. The maintainer chose `<!-- -->`: no
collision, the strongest comment prior after C's.

Rules. The pre-lexer counts `<!--` and `-->` as a pair, so block comments nest — unlike
HTML, whose readers will expect otherwise. The interior is raw text, never parsed:
commented-out code is usually broken code. It is a node holding that text, so the printer
returns it and the printer law holds (the pre-lexer used to drop `⟦ ⟧`, which lost the
text on the first print). `<!--` and `-->` can never be names. The ASCII spelling of S28
(`#| |#`) is superseded. Its purpose is switching code off; prose comments are the `;`
levels (a standalone `;` line is not allowed and a `;;` line becomes the next node's doc,
so disabled code needs its own form). Disabled code in a commit is reported, never
refused, because the log already keeps what was removed. For code that still parses,
`[ … ] drop` disables it and keeps it checked. FML, the prose profile, may want HTML
comments for its own layer ([FML](02.03.04-fml.md)); inside prose `//` is plain text.

**Comments are never obligations.** A comment never changes what a program means — the
inert-reader principle applied to the source itself. `;;` may *become* a word's `doc`
entry, which is documentation; a comment the checker reads as an obligation is code in a
comment's clothes. See [entries, checks and forcing](02.03.08-entries-checks-forcing.md#1-entries-s44-s45).
