# 02.05.07 2026-10-21 - Playground tracing

The /try playground grows toward an IDE. Two views of one run, both off unless asked for.

## Perfetto

`.wasm/fpl_trace.py` (shipped in the playground wheel) runs the tangled walker the
playground uses and returns the output and Chrome trace-event JSON: a slice per pass
(lex, parse, desugar, elaborate, evaluate, print), a slice per run line with its fuel, an
instant per call of a defined word with the fuel spent so far, and a `fuel` counter; a
refusal is kept in `otherData.failure`. The walker is not edited: while a run is traced,
`step` of `fpl.evaluate` is wrapped, so an untraced run is the walker as it is and pays
nothing. The **Trace** button runs it in Pyodide and opens ui.perfetto.dev through the
documented PING/PONG `postMessage` handshake (assets/fpl-trace.js). Demo:
`assets/try/demo.trace.json`, loadable by drag and drop into ui.perfetto.dev.

Calls are instants, not slices: the walker rewrites a call into its body and keeps no
return marker, so a duration per call needs a real call stack (open item). Events past
200 000 are counted, not kept.

An earlier Perfetto viewer for dependency-graph tracing was looked for in every ref of
`git log -S perfetto --all` and in the working trees: it is not there, so this is new.

## Trace panel and /ide

The dock (dockview, `assets/fpl-dock.js`) has a fourth panel, Trace, full-width below
Edit/Term; `assets/fpl-flame.js` draws four lanes from the events: passes, run lines (width
is wall time), a tick per word call, and fuel spent as a line, with an Open in Perfetto
button. `.wasm/assemble.sh` publishes the playground page a second time as `ide/`.
RemedyBG and the RAD Debugger (watch visualisers, timeline views) are the models for the
next panels (stepper, watch); they are not yet studied from primary sources.
The saved-layout key moved to v3 so an old saved layout does not hide the panel.
The sample buffer's `dup ∗` uses a Unicode asterisk the lexer refuses: the sample fails
at line 13 (pre-existing).

## Sentry

`assets/fpl-telemetry.js` loads the pinned CDN bundle `bundle.tracing.min.js` (10.20.0,
with SRI) only when `window.FPL_CONFIG.sentryDsn` is set. The committed
`assets/try/fpl-config.js` is empty; `.wasm/assemble.sh` writes the DSN from the
`FPL_SENTRY_DSN` environment variable at build time. `runFpl` and `runTraced` run inside
`Sentry.startSpan`; `recordPasses` replays the interpreter's pass slices as child spans
(`fpl.pass`). Their absolute times are approximate: they are laid back from the end of
the run, because the Python clock and the page clock differ.

## Measured

Program: 100 run lines of `1 [dbl inc dbl inc] 20 repeat`, best of 15, CPython, whole run
including lex to print (`.wasm/bench_trace.py`): untraced 234-251 ms, traced 401-450 ms,
x1.6 to x1.9, 16 108 events; the traced figure includes building the JSON. Untraced runs
pay nothing by construction. In Pyodide a small run traced end to end in headless Chrome:
6 passes, output correct, trace opened in ui.perfetto.dev (puppeteer-core, 2026-10-21).
Not measured: Pyodide overhead on large runs, and the Sentry SDK's own cost.
