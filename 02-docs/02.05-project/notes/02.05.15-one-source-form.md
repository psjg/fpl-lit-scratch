# 02.05.15 2026-10-27 — One source form: .fpl and .fml

with Python docstring conventions, went through literate programming and the nbdev, Sphinx,
Quarto and Marimo tool chains, and ended with FPL itself. The maintainer's own turns carry the
decisions; the other side's turns carry proposals. This note records where he ended, which
parts of it are his words and which are consequences drawn after his last turn, and what the
tree already says. Nothing here is ratified as an ADR.

## The position

In his words, in three steps. First, what FPL is:

> nou kijk wat ik bedoel is dat FPL dus twee dingen is en dat is waar we eigenlijk mee waren begonen:
>
> 1. symbolisch gestructureerde semantiek via o.a. doc comments.
> 2. een tangle en weave van markup die ook semantisch / symbolisch gekoppeld kan worden zodat we echt literate programming eindelijk ooit een keer goed doen.

Then, where the tool chain goes:

> eigenlijk alles wat we met deze hele spaghetti soep (noedel soep) aan tooling doen naar gewoon een duidelijke .fpl / .fml format

And last, sharper than the proposal it answered (which kept tangle, weave and an interactive
view as three projections of one graph):

> nee de tangle en interactiviteit zijn dus ook weg het is gewoon allemaal een tooling we kunnen wel werven naar inferieure export formats zoals een site of een pdf (maar die zijn ook gewoon onderdeel van de tooling zegmaar)
>
> en gewoon alles in een ding denk ik alles wat .fpl is is ook .fml maar dan met een inversie van comments of niet etc

So: **one source form.** An `.fpl` file and an `.fml` file are the same language. They differ in
the lexical default only: in `.fpl` code is unmarked and prose is marked; in `.fml` prose is
unmarked and code is marked. Tangle, weave and interactive views are not concepts of the
language; they are tools. A site or a PDF is an export, and an inferior one.

## Consequences

The first four follow from his words directly. The fifth is his decision of 2026-10-27 13:50,
given after the conversation. The sixth was drawn in the reply after his last turn, which he did
not answer; it is recorded, with local bias switching below, as a consequence to test, not as his.

1. **Same AST, same names, same checker.** `parse(f.fpl)` and `parse(f.fml)` give the same kind
   of tree: one name resolution, one type checker, one module graph. Nothing is checked in one
   form that is not checked in the other. This is FON's position applied to prose: there is one
   native tree ([ADR-0003](../adr/ADR-0003-fon-is-an-fpl-subset.md),
   [ADR-0004](../adr/ADR-0004-native-abts-fon-at-boundaries.md)), and every file form is a
   spelling of it.
2. **A doc comment is a node, not a comment.** The documentation above a definition is a child
   of the definition: text runs and `Ref` nodes that point at symbols, not a string that a
   later tool scans for names. A reference to `Scope` is an edge to the symbol `Scope`, so a
   rename moves it. The conversation wrote this as Rust's `///`; the spelling in the tree is
   `;;` on a definition (S33 revised,
   [spellings and comments §5](../../02.03-reference/02.03.06-spellings-and-comments.md#5-comments-s33-s48)),
   and the point is the shape of the node, not the glyph. The typed fields are
   [DI-0054](../inbox/DI-0054-doc-fields-are-symbolic-edges.md).

   **Syntax caveat.** Every code sample in the conversation is the other side's invention; it
   has never seen FPL's grammar. The samples show what a doc node or a projection should carry,
   not how it is spelled. The real forms are in the
   [FML reference](../../02.03-reference/02.03.04-fml.md) and in
   [spellings and comments](../../02.03-reference/02.03.06-spellings-and-comments.md).
3. **Documents are views over the graph; document order is not storage order.** What a reader
   sees in which order is a query over definitions, docs and examples, so the order an
   explanation wants and the order a program wants do not have to be the same file. This is
   the old conflict of literate programming, and the answer here is not to pick one.
   [DI-0055](../inbox/DI-0055-documents-as-views-over-the-graph.md).
4. **Tangle is a projection, so the bootstrap's literate tool is scaffolding.** A compiler asks
   for the program-relevant part of the tree, a site generator asks for the publication part;
   neither is more basic than lowering to a machine. Today the walker's pages are tangled to
   Python by `lit` (`.harness/tools/lit/`) and `03-fpl/*.md` to `.fpl` by
   `01-bootstrap/tangle_fpl.py`, and published through Quarto, Marimo, Obsidian and OKF. All of
   that is bootstrap tooling. It is research data for the language: harvest what each tool
   found, then drop the tool (table below).
5. **HTML, PDF and the other publication formats are compiler targets, like RISC-V or WASM.**
   The maintainer's decision of 2026-10-27, in his words "html is een compiler target". An
   export is a backend in the sense
   of the [backend plan](02.05.12-backend-plan.md), one more pass at the end of the pipeline
   graph ([ADR-0012](../adr/ADR-0012-pipeline-is-a-computation-graph.md)), not a view the
   source is organised around.
6. **The two printers are involutive, as a testable invariant.** With `print_fpl` (code first)
   and `print_fml` (prose first) over the same tree:

        parse(print_fpl(x)) ≡ x
        parse(print_fml(x)) ≡ x        modulo formatting

   so `.fpl` and `.fml` may differ lexically, never semantically, and an editor can switch
   "view as FPL" and "view as FML" without a conversion step and without two sources to keep
   in sync. This is a property test over generated trees, the same kind as FML's two printer
   laws today.

## What the tree already holds

Much of this was in FML from 2026-09-28, and the position sharpens it rather than replacing it.
The [FML reference](../../02.03-reference/02.03.04-fml.md) already says FML "is not a second
language: it is the FPL grammar with the polarity of prose and code swapped"; its §2 already
calls tangle and weave "two print profiles on one tree" with `parse ∘ print = id` as the tangle
guarantee; and it already says `mean/doc` needs no separate field because the doc of a
definition is the prose its island sits in.

The delta of 2026-10-27:

- **Tangle and weave are no longer named profiles of the language.** FML §2 and F20 count four
  print profiles (full, tangle, weave, interface). In the new position, "tangle" and "weave"
  are words for what tools do; the language has one tree and the two lexical defaults.
- **The law spans both forms.** FML's printer laws hold within the prose form; consequence 6
  asks for one tree printed both ways and read back to the same tree.
- **The doc node is typed.** FML treats a definition's doc as the prose around it; the
  conversation makes the references in that prose, and the fields of a doc, edges in the
  graph ([DI-0054](../inbox/DI-0054-doc-fields-are-symbolic-edges.md)).
- **The bootstrap's documentation chain has a status:** scaffolding and research data, not a
  design to grow.

## Considered and set aside

**A migration to canonical `.ipynb` with nbdev, MyST-NB and Sphinx.** Mid-conversation, with
refactors held cheap, the proposal was to make Jupyter notebooks the one canonical authoring
format: nbdev exports Python modules and runs the notebook tests, MyST-NB lets Sphinx read the
notebooks directly (so there is no `.ipynb`-to-Markdown sync), and Quarto, Marimo and Obsidian
become generated targets. A capability-preservation matrix judged most projections strictly
preserved, Marimo only under a Marimo-compatible subset of notebooks (one global definition per
symbol, no cycles), and Obsidian only as a read-only projection. It was set aside because the
maintainer's later turns moved the authority out of every external format: if `.fpl` and `.fml`
are the one source, a canonical notebook is a second language to keep in step, and nbdev,
Sphinx and Quarto are prototypes of tooling, not its core. The same holds for an Obsidian
plugin as a structured editor; he judged that effort better spent once FPL is bootstrapped.

## Open questions

- **The minimal uniform syntax model.** What is the least model in which prose, code, symbolic
  references, definitions, claims, examples and executable expressions sit side by side with no
  code/markup boundary? FML's islands, `“ ”` interiors and the pre-lexer are the current
  answer for one direction; whether the same pre-lexer serves both defaults is not shown.
- **Local bias switching.** Can a region switch its default locally, as quotation and
  unquotation do (Lisp's quasiquote, FML's `⟨ ⟩` island in prose and `“ ”` in code)? If so,
  how deep may they nest, and does the printer pick the outer default per file or per region?
- **What a `.fml` file's first-class document nodes are** (section, claim, example, figure) and
  which of them the checker reads; FML F12 (does a heading open a section) is the same question.
- **When the scaffolding goes.** Which tool is dropped first, and what replaces its gate, is for
  a design note once FPL can read its own pages ([DI-0042](../inbox/DI-0042-merge-literate-draft-back.md)).
