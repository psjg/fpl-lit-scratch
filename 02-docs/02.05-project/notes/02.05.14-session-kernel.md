# 02.05.14 The session kernel

[ADR-0006](../adr/ADR-0006-one-fpl-executable.md) names three frontends: `fpl repl`, `fpl tui` and `fpl pty`. They differ in how a person or an agent sits at the session, not in what a session is. This note fixes what they share, so that the web IDE ([DI-0045](../inbox/DI-0045-editor-and-repl-session-collapse.md)) can become a fourth without a second design.

## What a session is today

A session is a log file ([01.01.06](../../../01-bootstrap/01.01-boundary/01.01.06-cli.md), `fpl/log.py`): events in order, each an input with its output, an error, or a rewind, appended under a lock and made durable before anything is printed. The state at an event is every accepted input its deps lead back through, run again as one file (`fpl/session.py`). So the state is derived from the log, not held beside it: a process holds nothing a restart cannot read back. The cost is the same: an input replays the whole program, so a turn is O(program). A kernel that keeps the evaluated image warm is a later optimisation, and the protocol below does not change when it arrives.

## The kernel

One process per named session, started by the first frontend that needs it. It owns the log path of the session and a unix socket beside it, and it serialises turns: one input is evaluated at a time, by the same code `fpl repl` runs (`fpl.repl`), so the three frontends cannot disagree about a result, a head check or a refusal.

Where the files live: `$XDG_STATE_HOME/fpl/sessions/NAME.log` (default `~/.local/state/fpl/sessions/`) for the log and `$XDG_RUNTIME_DIR/fpl/NAME.sock` for the socket, with the state directory standing in when there is no runtime directory. A session name is `[A-Za-z0-9][A-Za-z0-9._-]*`; anything else is refused, not rewritten.

The kernel is the one holder of an exclusive lock on `NAME.sock.lock` for as long as it lives, so two frontends that start it at once get one kernel and the lock dies with the process; a socket file found by the holder is a dead kernel's and is replaced. Every connection has a writer thread and a bounded queue: a watcher that stops reading is dropped when its queue is full, and cannot hold up the client whose feed it hears.

### Protocol

JSON lines, one object per line, UTF-8, over the unix socket (a pipe to a child works as well, the framing is the same). A request has an `op` and an `id` the client chooses; every response to it carries the `id`, and the last carries `"status": "done"`, or `"status": "error"` with an `error` text; a refusal carries the `id` of the request too. These are nREPL's request and response conventions ([nREPL design overview](https://nrepl.org/nrepl/design/overview.html): "fundamentally message-oriented and asynchronous", `:op`, `:id`, `:status` with `done` on the final message), spelled as JSON, which every agent already parses.

| op | request fields | response |
| --- | --- | --- |
| `hello` | none | `session`, `head` (events so far), `fuel` (the default budget) |
| `feed` | `text`, optional `fuel`, `who` (`model`, `session`) | `turns`: for each input in `text`, `input`, `out`, `notes`, `code`, `spent` (steps, or null), `ms`; and `transcript` |
| `replay` | none | `transcript` of the whole log |
| `log`, `show` | none | the `--log` or `--show` listing of the REPL, as `out` |
| `rewind` | `event` | as `--rewind` |
| `watch` | none | acknowledged; from then on every `feed` by any client is pushed to this connection as an `event` message |
| `stop` | none | the kernel closes its socket and exits |

`watch` is the one idea taken from Jupyter: its kernel has a request channel per client and one broadcast channel, `iopub`, that every attached client sees ([Jupyter messaging](https://jupyter-client.readthedocs.io/en/stable/messaging.html): shell, control and IOPub channels; a client sees the outputs of executions other clients ran). Here the broadcast is not a second socket but a flag on a connection. An agent that evaluates and a person who watches in `fpl tui` see one session.

Provenance is per request: a `feed` carries the `FPL_MODEL` and `FPL_SESSION_ID` of the client, which the REPL records on the event as it does for its own process (`who` is `agent` when either is set). The kernel's own environment is not the author.

### The transcript form

The transcript is the program and its results in one text, the round-trip of [DI-0022](../inbox/DI-0022-repl-transcripts-round-trip.md) with the judgement lines of [DI-0023](../inbox/DI-0023-repl-results-as-judgement-claims.md): an input is written as it was entered, each line the input printed follows as `|= <line>`, and a note (a goal met, the caret under an error, the new head) follows as a `;;` comment line.

    1 2 +
    |= [ 1 2 + ]
    ;; HEAD 1 $45600:...

The reader of `feed` swallows a line that starts with `|= ` at column 0 before it splits the text into inputs. So a transcript fed back in is the program it came from, and a pasted session is a fixture. Swallowing is not checking: a `|=` line is not yet a claim that re-running compares with the result. That is the next step of DI-0023 and needs the checker, not another frontend.

## The frontends

- `fpl repl` is the existing line REPL, run in the process of the terminal. It does not need a kernel and keeps working without one.
- `fpl pty --session NAME` finds the kernel of `NAME` (starting it detached if there is none), then speaks the protocol: a piped stdin is one `feed` and the transcript of its turns goes to stdout, so `echo '1 2 +' | fpl pty --session x` is a complete call for an agent; at a terminal it replays the log on attach and then reads blocks separated by blank lines. `--watch` prints the events other clients cause, `--replay` prints the log first when piped, `--stop` ends the kernel.
- `fpl tui` is the Textual application: one editor pane that is also the transcript, in the sense of [DI-0045](../inbox/DI-0045-editor-and-repl-session-collapse.md): Shift-Enter evaluates the cell under the cursor and writes its `|=` lines indented under it, in the buffer, replacing the lines of an earlier evaluation, as the BQNPAD of [DI-0044](../inbox/DI-0044-bqnpad-as-model-for-ide-repl.md) does. Beside it the transcript pane shows the replay of the session, below it the trace and stepper panes (stubs until the tracer of [02.05.13](02.05.13-playground-tracing.md) has a terminal form), and a status bar with the head, the fuel spent and the milliseconds of the last turn. Everything has a key; there is no mouse-only path. In a terminal that cannot run it (`TERM=dumb`, or no tty) it says so and exits 2, and points at `fpl repl` and `fpl pty`.

## Open

- What "the state at this line" means when an edit above it changes the program below: today Shift-Enter appends the cell as a new input at the head, which is a transcript, not an edit-and-replay document. DI-0045 keeps this open.
- Instant evaluation while typing ([DI-0044](../inbox/DI-0044-bqnpad-as-model-for-ide-repl.md)) needs the deadline next to the fuel and an effect-free line; the kernel has the budget, not the deadline.
- A kernel that keeps the image warm, to make a turn cheaper than the replay of the program.
- Authentication beyond the file mode of the socket (0600 under a 0700 directory).
- `|=` as a checked claim.
